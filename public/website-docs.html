System Components

🔀
Load Balancer
Nginx distributes 500 concurrent users across API servers using Round Robin. Handles SSL termination and edge-level rate limiting.
Nginx / AWS ALB
⚡
API Servers
Stateless Node.js + Express containers. Validate URLs, check Redis cache, and enqueue jobs to BullMQ. Scale horizontally with no config changes.
Node.js · Docker
🔴
Redis Cache
Shared cache-aside store with 5-min TTL across all API servers — eliminates per-process cache fragmentation of current NodeCache setup.
Redis 7 · Sentinel
📋
BullMQ Queue
Redis-backed job queue decouples HTTP layer from expensive fetches. Supports retries (3x), exponential backoff, and dead-letter queue.
BullMQ · Priority
🔧
Worker Processes
Pull audit jobs from BullMQ, fetch external websites, parse HTML, and save results to Redis + PostgreSQL. Scale independently from API servers.
Worker Threads
🗄
PostgreSQL
Audit history, analytics and logs. Primary + Read Replica with PgBouncer connection pooling. JSONB columns for flexible audit data.
PostgreSQL 16

Data Flow — Two Paths

⚡ Cache Hit Path (most requests after warmup)

1
Client sends POST /audit with URL to audit
2
Load Balancer routes to least-loaded API server
3
API Server validates URL with Zod, generates Request ID
4
Redis → Cache HIT → Returns cached result immediately <5ms

🔄 Cache Miss Path (first request for a URL)

1
API Server checks Redis → MISS → enqueues job in BullMQ, returns 202 + jobId
2
Worker picks job → fetches external website (5s timeout) → parses HTML
3
Redis + PostgreSQL updated. Client polls GET /audit/status/:jobId → gets result

D2

Technology Decision Record

Why each tech was chosen, alternatives considered, and why they were rejected

25 Marks

Click any card to expand the full decision rationale.

TDR-01Runtime — Node.js 20 LTS ✓ Chosen▾
Why Chosen
  • Non-blocking I/O — ideal for URL fetching (I/O-bound)
  • Event loop handles thousands of concurrent connections
  • Same language (TypeScript) frontend + backend
  • Vast ecosystem: axios, BullMQ, Pino, Zod
Alternative Rejected
Python (FastAPI)
Why Rejected
  • GIL limits true concurrency in CPU-bound workers
  • Slower Docker cold start
  • Two languages in one project
TDR-02Web Framework — Express.js ✓ Chosen▾
Why Chosen
  • Minimal, un-opinionated — full control over middleware
  • Fastest startup time among Node.js frameworks
  • Battle-tested in production since 2009
  • Easiest to containerize horizontally
Alternatives Rejected
NestJS — Too complex (DI, decorators, modules) for a single-feature API
Fastify — Smaller ecosystem, less familiar to most devs
TDR-03Caching — Redis 7 ✓ Chosen▾
Why Chosen
  • Sub-millisecond latency (<1ms reads)
  • Shared across all server instances
  • Native TTL per key — perfect for cache expiry
  • Also powers BullMQ — dual-purpose infrastructure
  • Redis Sentinel for high availability
Alternatives Rejected
NodeCache (in-memory) — Not shared between servers; lost on restart
Memcached — No persistence; can't run BullMQ on top of it
TDR-04Job Queue — BullMQ ✓ Chosen▾
Why Chosen
  • Uses existing Redis — no new infrastructure needed
  • Built-in retries, backoff, DLQ, priority queues
  • TypeScript-native, full type support
  • Bull Board dashboard for real-time queue monitoring
Alternatives Rejected
RabbitMQ — Extra AMQP broker; overkill for 10k/day scale
AWS SQS — Vendor lock-in, extra latency, cost
Kafka — Designed for millions/sec; extreme overkill here
TDR-05Database — PostgreSQL 16 ✓ Chosen▾
Why Chosen
  • ACID-compliant — audit results reliably stored
  • JSONB column for flexible audit data + indexing
  • Read Replica for analytics without primary load
  • PgBouncer for connection pooling
Alternatives Rejected
MongoDB — Schema flexibility not needed; fixed audit shape
MySQL — Weaker JSONB support, less powerful EXPLAIN tooling
TDR-06Load Balancer — Nginx ✓ Chosen▾
Why Chosen
  • SSL termination + load balancing in one binary
  • ~2MB memory footprint — extremely lean
  • Built-in rate limiting, gzip, static serving
  • Portable across all cloud providers
Alternatives Rejected
AWS ALB — Vendor lock-in, cost even when idle, less routing control
HAProxy — Nginx does everything HAProxy does + more
TDR-07Language — TypeScript (strict mode) ✓ Chosen▾
Why Chosen
  • Compile-time type errors — fewer runtime bugs
  • Zod v4 schemas auto-generate TypeScript types
  • IDE autocomplete speeds development significantly
  • Self-documenting — types serve as inline contracts
Alternative Rejected
JavaScript (plain) — No compile-time safety; debugging runtime type errors in production is very costly
D3

Failure Mode Analysis

Top failures, their cascading impact, and concrete mitigations using FMEA methodology

25 Marks
🔴 Critical Failure 1 — External Website Timeout / Unreachable Risk: 5×5 = 25

Most common failure — audited URL doesn't respond. Without protection, workers hang indefinitely, exhausting the thread pool and cascading to total service failure.

Effects Without Mitigation
Worker threads hang indefinitely
Thread pool exhaustion → service unresponsive
Queue backs up → cascading failure
All users affected, not just slow URL
Mitigations
5s hard timeout per fetch ✅ Implemented
p-limit: max 50 concurrent fetches ✅ Implemented
Structured TIMEOUT/UNREACHABLE errors ✅ Implemented
Circuit Breaker: stop fetching failing domains 30s
BullMQ retry: 3x exponential backoff (1s, 2s, 4s)
Dead Letter Queue for permanently failed jobs
External website slow/down ↓ 5s timeout fires (axios AbortController) ↓ Return TIMEOUT error immediately to client ↓ BullMQ retry: after 1s → 2s → 4s ↓ All 3 retries fail → job moves to Dead Letter Queue ↓ Alert: "URL unreachable after 3 attempts"
🟡 High Failure 2 — Redis Crash / Unavailability Risk: 3×5 = 15

Redis powers both caching AND BullMQ — a dual-risk failure point. A crash means cache goes cold AND no new jobs can be queued.

Effects Without Mitigation
Cache gone → 10-100x latency spike on all requests
BullMQ broken → audit requests fail entirely
Rate limit counters lost → abuse possible
Mitigations
Graceful fallback: direct fetch if cache down ✅ Implemented
Redis Sentinel (3-node): auto-failover <30s
AOF persistence: no data loss on crash
Separate Redis: cache vs. queue instances
Health check ping → 503 if Redis unreachable
PagerDuty alert within 30 seconds
Redis Primary OOM crash detected ↓ Sentinel detects failure (within 5 seconds) ↓ Promotes Replica 1 to new Primary automatically ↓ ioredis auto-reconnects all API servers ↓ Cache cold → first requests hit live websites ↓ Cache warms up over ~5 minutes ↓ Full recovery: <2 minutes total downtime
🟡 High Failure 3 — Traffic Spike / Overload (DDoS / Viral) Risk: 4×4 = 16

Sudden traffic spike to 500+ concurrent requests. Without protection, OOM kills Node.js process and all users get 503.

Effects Without Mitigation
Event loop blocked by too many fetches
OOM kill — Node.js process crashes
503 errors for ALL users
Queue backup of thousands of jobs
Mitigations
Rate limiting: 100 req/min per IP ✅ Implemented
p-limit: 50 max concurrent fetches ✅ Implemented
503 SERVER_BUSY when overloaded ✅ Implemented
Nginx edge rate limit: 500 req/sec global
K8s HPA: CPU > 70% → new API server in <60s
BullMQ buffer: burst queued, processed steadily
Traffic spike: 2000 req/min detected ↓ Nginx: reject requests > 500 req/sec (429) ↓ Rate limiter: 100/min per IP → most bots blocked ↓ Remaining → BullMQ queue (buffered safely) ↓ Auto-scaler: CPU 80% → 2 new servers spin up (<60s) ↓ New servers join load balancer pool ↓ Queue drains, latency normalises ↓ Post-spike: extra servers terminated (cost saved)

Rollback Plan — Blue/Green Deployment

Every deploy uses Blue/Green strategy. If a bug is detected post-deploy, rollback completes in < 5 minutes with zero data loss.

1
🚨 Detect — Automated (within 2 min)
Grafana alert fires: 5xx error rate > 5% post-deploy. PagerDuty incident created automatically. On-call engineer gets SMS + push notification.
2
🔍 Triage — Human (1 min)
On-call checks Grafana dashboard, confirms regression is deploy-related (not external), and triggers rollback via Slack command or Render dashboard.
3
⚡ Execute Rollback — Automated (< 2 min)
Previous stable Docker image is redeployed. Traffic shifted back to v1.2 while v1.3 is quarantined.
# Render.com render deploys rollback --service page-pulse --deploy-id <prev-id> # Kubernetes kubectl set image deployment/page-pulse app=page-pulse:v1.2 kubectl rollout status deployment/page-pulse # Verify curl https://page-pulse.onrender.com/health | jq '.version' # Expected output: "1.2.0"
4
✅ Verify & Recover
Error rate drops to <1% within 60s of rollback. PostgreSQL and Redis state unaffected — no data loss. Post-mortem scheduled within 24 hours.
